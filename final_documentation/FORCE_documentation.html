Abstract
FORCE is an embedded elderly-care system mounted on a standard forearm crutch. It continuously monitors heart rate, blood oxygen saturation, and body temperature via optical sensors, detects falls through a multi-stage IMU-based algorithm, and transmits live telemetry to a caregiver dashboard via BLE and a REST API server. All firmware, sensor housings, and mounting hardware not provided at the start of the contest were custom designed and 3D-printed by the team.

System Overview

FORCE is a full-stack assistive health monitoring system built around a standard forearm crutch. The system spans three layers — embedded firmware on an ESP32 microcontroller, a local REST API server, and two mobile applications — forming a closed telemetry loop from sensor to caregiver screen.

System Architecture at a Glance
Fig. 1.1 — End-to-end system data flow. All local sensor processing and fall detection execute on the ESP32.
Design Principles

The firmware is written in C++ using the Arduino/ESP-IDF framework and structured as a cooperative task scheduler — a lightweight array of Task structs, each carrying an interval and a function pointer, ticked by runTaskScheduler() in the main loop. Tasks range from 100 Hz IMU reads to 3-second temperature polls, with no RTOS overhead.

All fall detection logic executes entirely on the ESP32, with no cloud round-trip in the critical path. A fall alert reaches the caregiver's phone within approximately 500 ms of sensor data confirming the event — irrespective of server latency.

Custom Hardware

Every physical component not provided at contest start was custom-designed and 3D-printed by the team: the IMU enclosure at the crutch tip, the sensor handle housing integrating the MAX30102 optical window and MAX30205 probe, the OLED display bracket, and all PCB mounts and cable guides. The crutch frame itself is a standard forearm crutch.

Hardware Architecture

All sensors communicate over a shared I²C bus (SDA = GPIO 21, SCL = GPIO 22, 100 kHz) with the exception of the touch input, which uses the ESP32's native capacitive-touch peripheral, and the buzzer, which is driven directly from a GPIO via the tone() API. The MPU-6050 additionally uses a dedicated interrupt line (GPIO 4) to signal data-ready at 100 Hz, eliminating polling overhead.

Physical Placement
Handle Assembly (top) The MAX30102 pulse oximeter and MAX30205 body temperature sensor are co-located in the custom 3D-printed handle. Sustained palm contact gives the optical sensor a stable skin window and keeps the thermistor in conductive contact with the user's hand. The capacitive touch pad, panic button, OLED display, and mirror button are all handle-mounted for single-hand operation.
Crutch Tip (bottom) The MPU-6050 IMU is housed in a 3D-printed enclosure at the crutch tip, as far from the user's hand as possible. This maximises the lever-arm effect: even small angular displacements at the tip produce large gyroscope readings, improving fall sensitivity. The tip enclosure is impact-rated for repeated ground contact.

Data Flow Architecture

The FORCE telemetry pipeline is a three-hop chain: ESP32 → Phone App → REST Server → Caregiver App. Each hop uses a different protocol optimised for its context — BLE for the low-power wireless link to the crutch, HTTP/REST for reliable server persistence, and polling REST for the caregiver dashboard.

Hop 1 — ESP32 to Phone App via BLE

The ESP32 acts as a BLE peripheral, advertising the FORCE service UUID and exposing five GATT characteristics. The phone app acts as the central/client. All notify characteristics push data at 100 ms intervals; the phone writes to the acknowledge characteristic to confirm panic receipt.

Fig. 3.1 — BLE GATT characteristic map and server endpoint binding.
BLE Packet Format

Numeric payloads are packed as raw little-endian IEEE 754 floats with no delimiters. The vitals characteristic carries 12 bytes (heart rate, SpO₂, confidence); the motion characteristic carries 24 bytes (ax, ay, az, gx, gy, gz), with accel values pre-scaled to g and gyro values pre-scaled to °/s before packing. This minimises BLE payload size while preserving full float precision.

Hop 2 — Phone App to REST Server

Every BLE notification received by the phone app triggers an HTTP POST to the corresponding REST endpoint at 172.20.100.35:8080, authenticated with a static Bearer token. The server persists all records to a PostgreSQL database with timestamps. Panic events carry an eventType of either PANIC_BUTTON or FALL_DETECTION, written by the phone app based on the value of the BLE panic characteristic (0 = manual, 1 = fall).

Hop 3 — REST Server to Caregiver App

The caregiver app polls the server via HTTP GET on /api/vital-signs/latest, /api/temperature/latest, and /api/panic-events/latest to populate the live dashboard. When a panic event appears with status: ACTIVE, the caregiver app issues a PUT /api/panic-events/{id}/acknowledge to mark it resolved, setting acknowledgedAt and transitioning status to ACKNOWLEDGED. This two-state lifecycle prevents repeated alerting from the same event.

Authentication

All POST endpoints require the header Authorization: Bearer esp32_static_token_12345. GET and acknowledge endpoints are presently unauthenticated, consistent with a closed local-network deployment where the server is not exposed to the public internet. The token is embedded in the phone app at build time.

Local Computing — Fall Detection

Fall detection is the most computationally intensive module and runs entirely on the ESP32 — no server round-trip is in the critical alert path. The algorithm is a four-stage sequential state machine evaluated every 500 ms, operating on a statically-allocated 60-sample ring buffer fed by the IMU at 100 Hz. Every stage imposes independent physical criteria; failure at any stage resets the pipeline to FALL_IDLE and clears the buffer.

Gate 0 — On-Body Verification (Precondition)

Before any fall processing occurs, Gate 0 must confirm the device is worn on a live human body. It runs continuously at 200 ms cadence and arms the pipeline only when either the capacitive touch pad detects grip or the MAX30102 reports skin contact (body.status == 3) with confidence ≥ 50%, sustained for a continuous 3-second window. Disarming requires both sources to fail for 10 seconds — an asymmetric hysteresis preventing momentary signal dropout from disarming the device mid-use. Disarming is blocked entirely while a fall event is being processed.

Fig. 4.1 — Fall detection pipeline. Buffer cleared and baseline invalidated on every reject/cancel path.
IMU Ring Buffer — Zero-Heap Design

The original implementation used std::queue<IMUData>, backed by std::deque, which heap-allocates memory in chunks — fragmentation-prone on a 300 KB MCU. The replacement is a custom IMURingBuffer<IMUData, 60>: 720 bytes of BSS, O(1) push (evict-oldest when full), O(1) indexed read, O(1) clear(), and a portMUX spinlock for safe concurrent access between the 100 Hz ISR drainer and the 500 ms scheduler task. Direct indexing also eliminated the full-buffer copy previously required by isFalling().

Kinematic Pattern Detector — isFalling()

isFalling() scans the full 60-sample ring buffer on every call, looking for three signals in a required temporal sequence. It is the single gate between FALL_IDLE and Stage 4.

Three Required Signals
Signal 1Descent anchor

A temporal reference point marking the start of fall dynamics. Two candidates are evaluated and the earlier one chosen:

Free-fall dip — accel magnitude below 0.73 g (< 3000 LSB). The crutch is briefly in free flight. Strongest physical indicator; used as anchor when present.

Peak rotation index — the sample of maximum gyro magnitude. Fallback for held-crutch falls, where the user's arm absorbs the descent and no weightlessness is observed. Always present when the gyro gate passes.

Signal 2 + 3Impact + sequence

Impact spike — accelerometer magnitude must exceed a mode-dependent threshold. Represents ground contact after descent.

Correct sequence — the descent anchor index must precede the impact index, and the gap must be ≤ 50 samples (500 ms at 100 Hz). This prevents an isolated hard knock from being linked to an unrelated rotation elsewhere in the 600 ms window.

Three-Mode Threshold Selection

The single most impactful false-positive reduction came from conditioning thresholds on grip state. The touch sensor is read at each evaluation, selecting one of three paths:

ModeConditionImpact thresholdGyro thresholdRationale
HELD Touch active 5700 LSB (1.39 g) 2460 LSB (150 °/s) Arm absorbs impact; mild tip kinematics. Often no free-fall dip. Lenient thresholds needed to detect held falls.
STRICT-A Unheld + free-fall 5700 LSB (1.39 g) 2460 LSB (150 °/s) Free-fall dip alone is strong evidence. Modest impact + rotation sufficient.
STRICT-B Unheld, no free-fall 8000 LSB (1.95 g) 5740 LSB (350 °/s) No kinematic separator from hard knock. Recorded false alarm: 310 °/s — below gate. Real falls: 486+ °/s — above it.
Stage 4 — Post-Impact Rest Verification

Stage 4 opens a 3-second window after pattern detection and requires two independent sub-gates to pass:

Sub-gate ASustained stillness · 1 s

The 10 newest samples must all show accel magnitude in 2900–5300 LSB (0.71–1.29 g, gravity ±29%) and gyro magnitude below 2500 LSB (152 °/s). The stillness clock resets on any motion, tolerating the 200–400 ms of natural crutch-tip angular momentum bleed-off after impact without rejecting genuine falls.

✓ lying still on ground ✗ arm swing continues
Sub-gate BOrientation change ≥ 30°

At pattern detection, the 10 oldest buffer samples are averaged into a pre-event gravity unit vector. After stillness passes, the 10 newest samples form a post-rest vector. The angle between them via dot-product cosine must exceed 30°.

Calibrated gap: hard-bounce false alarms change 1–5°; real falls change 60–100°. If baseline capture fails (edge case, early operation), sub-gate B is bypassed — fail-open, favouring user safety.

Stage 5 — Countdown & Alerting

On Stage 4 passing, a 20-second countdown is displayed on the OLED. A fresh short press of the panic button (rising-edge detected, not level-held) cancels and resets the pipeline. After cancellation, a waitingForRelease lockout prevents the still-held button from immediately re-arming the manual panic alarm. If the countdown expires, sendPanic(isFall=true) notifies the phone over BLE and the full three-phase buzzer alarm activates. Recovery requires a 3-second button hold.

Conclusion

FORCE demonstrates that a production-quality elderly care monitoring system can be built on low-cost commercial embedded hardware, with all safety-critical computation executing locally on a microcontroller. The system successfully integrates continuous vital sign monitoring, fall detection, and caregiver alerting into a single wearable form factor — an ordinary forearm crutch — without requiring the user to carry or interact with additional devices beyond their existing walking aid.

Technical Achievements
Reliability

The multi-stage fall detection pipeline with three-mode threshold selection, orientation change verification, and Gate 0 on-body gating achieves significant false-positive suppression — rejecting hard-bounce knocks, deliberate crutch waving, and table-drop events that would trigger simpler threshold detectors.

Robustness

Every module includes sensor-failure recovery: the bio hub and temperature sensor check readiness on every tick and attempt re-initialisation automatically. The BLE stack re-advertises on disconnect. The cooperative scheduler ensures no single task can block others. The ring buffer's portMUX spinlock guarantees ISR/task data integrity.

User Safety

The 20-second self-cancel window respects user autonomy — avoiding unnecessary emergency dispatches — while the fail-open orientation bypass ensures a genuine fall is never silently discarded due to early-operation buffer edge cases. The escalating three-phase buzzer alerts bystanders even before the BLE notification arrives.

System Integration

The full-stack architecture — embedded firmware, REST API, phone relay app, and caregiver dashboard — demonstrates end-to-end integration from raw sensor LSB values to a human-readable alert acknowledgement workflow. The panic event lifecycle (ACTIVE → ACKNOWLEDGED) provides a complete audit trail of every alert, with timestamps for both event creation and caregiver response.

Limitations and Future Work

The current system operates on a local area network, limiting caregiver monitoring to the same Wi-Fi network. A production deployment would route the REST server through a cloud endpoint with TLS and proper authentication. The static Bearer token would be replaced with per-device certificate authentication. Threshold calibration was performed on a limited set of captured events; extended field testing across a broader demographic would allow statistical refinement of the STRICT-B gyro gate and the 30° orientation threshold.

Fall detection thresholds are currently fixed at compile time. An adaptive calibration pass — learning the device's resting orientation and typical gait signature from the first few minutes of use — would improve sensitivity for users with atypical gait or for crutches mounted at non-standard angles.

Summary FORCE is a functional, end-to-end elder care assistive device built within the constraints of a competition timeline. The firmware architecture, sensor integration, and fall detection algorithm represent production-quality engineering decisions grounded in physical measurement, empirical calibration, and explicit safety tradeoffs. All sensor housings, mounting hardware, and PCB enclosures were custom designed and 3D-printed by the team from Politehnica University of Timișoara.
